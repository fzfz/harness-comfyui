# 实验工作台：运行迭代、跨工作区引用与 Agent 执行要求

## 1. 领域名词与关系

### 1.1 业务对象

1. Workspace、Session、Generation Run、Saved Media 沿用 [CONTEXT.md](../../CONTEXT.md) 的定义。本计划将 Generation Run 简称为 Run。

| 名词 | 定义 | 关系 |
| --- | --- | --- |
| 工作 | 用户组织创作目标、分支和结果的集合。 | 工作区保存工作；工作保存分支。 |
| 分支 | 用户保存一组准备运行的输入，并浏览相应结果的位置。 | 分支起点记录来源；后续任务可以选择其他参考记录。 |
| 任务 | 用户向 Agent 发起的一次执行请求。 | 任务属于创建时的当前分支，可以读取多个工作区的参考数据。 |
| Agent 预设 | Harness 加载的工具组件、角色提示词、MCP 与 Skill 组合。 | 配置中心为功能选择预设；同一预设可以用于多个功能。 |
| 原生 Tool | 通过 Harness 工具注册表向模型提供的可调用能力。 | 预设加载工具组件，宿主按 Agent 作用域提供工具名称、描述和参数声明。 |
| 参考来源 | 本次任务采用的历史任务、Run、经验或图片。 | 来源可以位于其他工作区，引用后保留原有归属。 |
| 经验 | 整个工作台共用、可以独立理解和使用的建议与适用条件。 | 任务可以同时采用多条经验；可选的来源与证据用于追溯和核验。 |
| 收藏 | 整个工作台共用的经验或 Run 收藏记录。 | 引用收藏时使用对应经验或 Run。 |
| 准备运行的输入 | 用户正在编辑或已经保存、供后续任务使用的参数。 | 点击“保存参数”后供任务提交使用。 |
| 任务固定输入 | 创建任务时保存的要求、参数和参考内容。 | 后续编辑分支时，已经创建的任务继续使用自己的固定输入。 |
| Workflow 输入图片 | 送入模板图片参数的图片。 | Host 根据图片绑定准备实际参数值。 |
| Agent 参考图片 | Agent 需要观察并按参考要求使用的图片。 | Agent 通过读图工具取得观察结果。 |
| 图片绑定 | 图片与模板图片参数的对应关系。 | 单图参数对应一张图片；多图参数按模板声明接收有序图片。 |

### 1.2 归属、来源与执行

1. 工作区用于组织和筛选内容。当前 Profile 内的任务、Run、经验和图片可以跨工作区引用。经验与收藏在整个工作台共享，工作区、会话和分支均作为来源信息。
2. 任务通过 Task ID 标识，并保存创建时的 `branch_id`。本任务的 Run 归入该分支。
3. 任务列表按所属工作查询；引用入口可以查询其他工作区的任务。
4. Run 保存实际执行工作区、分支、Task ID，以及调用方 Session、Turn 和 Tool Call。调用出处与结果归属分别记录。
5. Session 为 Agent 提供执行上下文。来源查询按记录 ID 定位，生成结果按任务所属分支保存。
6. 分支树继续表达当前工作的分支关系。从其他工作区使用 Run 创建分支时，用户指定目标工作和父分支；来源 Run 保留原有标识。

## 2. 总目标

1. 用户可以区分编辑中的输入、已保存输入和历史 Run 输入。
2. 用户可以从任意工作区选择参考任务、Run、经验及图片，并填写本次改进要求。
3. 用户在当前分支发起任务，运行结果自动归入该分支。
4. 用户通过选图控件添加单张或多张图片，并指定图片用途与模板参数。
5. Agent 能从当前任务读取全部执行依据，通过已有工具查询来源、读取图片、提交产物和持续实验。
6. 上部“经验”和“收藏”页签显示整个工作台的记录，用户可以一次引用多条经验或收藏。
7. 每个页面操作对应明确的数据写入、Agent 行为和可观察结果。
8. 配置中心的 10 种任务提示词满足第 5.4.1 节的内容要求；预设按该节装配原生 Tool。
9. 实施者通过真实 Agent 调用、实际产物和页面结果验收 10 种任务功能及第 5.4.5 节的提示词翻译。

## 4. 面临的问题

1. 任务和 Run 的读取依赖调用会话的工作区，限制了跨工作区引用。
2. 当前引用关系不足以固定一次迭代使用的任务产物、经验内容和图片用途。
3. 分支编辑与历史 Run 查看共用控件，用户难以判断保存时间和实际执行输入。
4. 手填图片路径无法表达多图选择、模板参数对应和跨实例文件准备。
5. Agent 获得图片名称时，仍缺少观察要求和使用目的。
6. 当前 10 种任务提示词缺少业务目标、数据采用方法和具体产物要求。
7. 提示词默认值与已保存的配置中心绑定分别存储。验收须核对新任务实际使用的执行要求。
8. 工作台任务读写尚未注册为原生 Tool，任务指令承担了 CLI 入口说明。预设的工具装配与任务目标须分别维护。

## 5. 问题的解决和实施方案

### 5.1 总架构图

1. 实施者按以下模块职责连接页面、任务、Agent 和生成服务。

   ```mermaid
   %%{init: {'flowchart': {'curve': 'linear'}}}%%
   flowchart TB
     UI[工作台页面] <-->|Remote 请求与状态轮询| WB[WorkbenchService]
     WB <-->|任务、分支、引用、产物| DB[(SQLite 与文件存储)]
     WB -->|预设 ID、模型、Task ID 与目标| HOST[Harness Agent 会话]
     PRESET[预设：工具、提示词、MCP、Skill] -->|按会话作用域装配| HOST
     HOST <-->|工具调用与结构化结果| TOOLS[工作台原生 Tool 组件]
     TOOLS <-->|读取任务、提交产物、结束实验| WB
     HOST <-->|现有生成与读图能力| RUNTIME[Generation Runtime / Image Reader]
     RUNTIME <-->|图片上传、生成与查询| COMFY[ComfyUI 实例]
     UI <-->|原文、翻译状态与译文| TR[提示词翻译服务]
     TR <-->|请求与最终回复| TH[翻译预设会话]
   ```

2. 前端沿用工作台 Remote 与 `refreshAfterMs` 轮询。Agent 运行期间，任务状态、图片准备状态、产物和 Run 变化继续返回页面。
3. 页面切换工作区只改变浏览位置。任务继续使用创建时保存的分支归属。
4. 工作台任务的 Agent 请求文字由配置中心的执行要求生成，只替换 Task ID。Harness 加载所选预设，向模型提供工具声明。Agent 通过原生 Tool 取得任务数据并提交产物。

### 5.2 数据结构与存储

#### 5.2.1 共享字段定义

1. 以下为本轮拟实施的字段定义。实施者在 `src/workbench/contract.ts` 和对应 schema 中维护结构；前端、原生 Tool、CLI 和 Host 共用同一份结构定义。

   | 字段 | 类型与含义 | 保存时机 |
   | --- | --- | --- |
   | `requirements.original_request` | `string`；原始需求。 | 保存准备输入、创建任务。 |
   | `requirements.instructions` | `string`；本次改进要求。 | 保存准备输入、创建任务。 |
   | `reference_task_ids` | `string[]`；用户直接选择参考的历史任务 ID。 | 添加引用后保存。 |
   | `reference_task_artifacts` | `{ task_id, artifact_id, artifact }[]`；本次采用的历史产物及内容。 | 创建任务时读取并固定。 |
   | `reference_run_ids` | `string[]`；用户直接选择参考的运行 ID。 | 添加引用后保存。 |
   | `reference_experiences` | `{ experience_id, title, conditions, note, provenance }[]`；本次采用的独立经验；`provenance` 定义见第 5.2.3 节。 | 创建任务时从经验记录读取并固定。 |
   | `image_refs` | `ImageRef[]`；本次输入的图片及用途。 | 导入或选图后保存。 |
   | `workflow_image_bindings` | `{ parameter_id, image_ref_ids: string[] }[]`；模板参数与有序图片的对应。 | 用户或 Agent 指定后保存。 |
   | `max_runs` | `integer`；本任务最多提交的 Run 数量。 | 创建任务时固定。 |

2. `ImageRef` 的字段定义如下。

   | 字段 | 类型与含义 |
   | --- | --- |
   | `image_ref_id` | `string`；本次输入中图片条目的标识。 |
   | `source` | `{ kind: 'run_media', run_id, media_id }`，或 `{ kind: 'uploaded_file', file_id }`。 |
   | `purpose` | `'workflow' \| 'agent' \| 'both'`；图片用途。 |
   | `reference_requirement` | `string`；Agent 需要观察、保留或改变的内容。 |

3. 任务输入根级沿用 `generation_input`、`prompt_input`、`parameter_mapping` 和 `base_model_id`，并增加本节的参考与图片字段。`task get` 在根级返回该任务的 `output_contract`。
4. 已保存的分支输入包含本节定义的参考字段。创建任务时，后端读取选中的任务产物、Run 和经验记录并固定内容；编辑分支只影响后续任务。
5. 图片来源的工作区、工作、文件名和缩略图为显示投影，由记录 ID 派生。前端提交实际记录 ID，后端读取对应内容。
6. 实施者从工作台分支准备输入、任务创建接口和生成输入产物中删除 `context_refs`。实施者同步删除该字段的工具说明及校验。历史任务与 Run 的原始记录继续保存；创建后续任务时，按本节定义组装输入。资源候选类型限定为 `model`、`lora` 和 `comfyui-template`。

2. 已有 `request_json` 继续用于历史查询。缺少图片用途的历史参数按原记录显示；用户选择图片后保存明确用途。

#### 5.2.3 经验的内容与证据

1. 经验正文须让 Agent 在阅读原始任务前就能判断用途。已有 `title` 表达经验主题，`conditions` 写明模型与场景。`note` 写明具体提示词或参数做法、已观察效果和适用局限。
2. `provenance` 记录每条经验自己的出处，字段如下。

   | 字段 | 类型与含义 |
   | --- | --- |
   | `created_by_task_id` | `string \| null`；整理该经验的任务 ID。人工整理或未记录来源时为空。 |
   | `evidence` | `{ run_id, generation_task_id, role }[]`；该经验对应的证据。 |
   | `evidence[].run_id` | `string`；被观察或评价的运行。 |
   | `evidence[].generation_task_id` | `string \| null`；产生该 Run 的任务，由 Run 记录解析。 |
   | `evidence[].role` | `'supporting_evidence' \| 'counterexample'`；支持记录或反例。 |

3. 来源可以为空，经验仍可保存、展示和引用。整理任务与产生图片的任务分别记录。
4. 添加经验引用时，准备输入只增加该条经验。用户直接选择的任务和 Run 才进入 `reference_task_ids`、`reference_run_ids`。
5. Agent 默认根据经验正文判断适用性。需要核验观察依据或适用条件时，Agent 再读取该条经验的 `provenance`。当前任务的原始需求与本次改进要求由 `requirements` 提供。
6. 整理经验的执行要求须指导 Agent 产出第 1 项要求的正文。页面沿用经验标题、适用条件和经验结论表单，供用户修改并保存。
7. 经验卡将“适用条件”和“经验结论”直接展示，将可选出处放入“来源与证据”。引用卡按经验保留这些关系。

### 5.3 跨工作区查询与任务执行

1. 工作台新增记录选择查询，接受类型、工作区、工作、任务和关键词筛选。未选择工作区时显示当前 Profile 内的记录。筛选只影响列表。
2. `workbench_task_get` 按 Task ID 读取任务；Run 输入和媒体查询按 Run ID 读取。来源位置由记录解析，查询不依赖调用会话当前所在工作区。
3. `workbench_task_get` 返回指定任务的输入、产物、问题回答及运行轮次；输入字段见第 5.2 节。历史任务只有提示词或参数产物时，也可以作为参考。
4. `workbench_task_publish` 沿用 `{ task_id, artifact }` 请求。Host 按 Task ID 保存产物，使用任务记录中的写入位置采用内容，并记录实际调用会话。
5. `generation submit` 通过清单根字段 `workbench_task_id` 关联任务。Host 从任务所属分支取得工作区，再调用 Generation Runtime。
6. `generation wait` 按每条 Run 的实际工作区登记观察。任务会话接收完成通知，并读取运行结果。
7. 图片预览、原图下载及媒体路由按媒体 ID 解析来源。任务列表与 Run 列表按所属工作显示；任务详情可打开各条跨区参考记录。
8. 配置中心决定本次任务使用的 Agent 预设、提供商、模型、推理等级和执行要求。创建任务时固定这份配置。
9. 运行任务提交 1 个 Run，`max_runs` 为 1。持续实验使用用户填写的次数上限，界面显示“最多运行次数”。
10. 原生 Tool 和受管 CLI 共用 [schema.ts](../../src/workbench/schema.ts)、[contract.ts](../../src/workbench/contract.ts)与 WorkbenchService。`output_contract` 的参数 ID 根据任务模板生成。`requested_skill` 沿用功能配置，`evaluation_input` 保存被评价 Run 的资料。工具装配与说明来源见第 5.4.1 节。
11. 页面展示任务的执行中、等待输入、成功或失败状态，并保留每次 Run 的实际结果。
12. 持续实验首轮使用固定输入，后续轮次读取本任务上一轮 Run 与评价，再提交候选输入。全部轮次归入本任务所属分支。

### 5.4 运行准备、来源引用与 Agent 产物

#### 5.4.1 预设工具装配与配置中心提示词

本节适用于第 5.4.3 节的任务功能。提示词翻译按第 5.4.5 节实施。

1. 实施者按以下职责组织 Agent 的输入。

   | 内容位置 | 负责内容 | 实施入口 |

   | Agent 预设 | 组合角色提示词、工具组件、MCP 与 Skill。 | 在预设组合中加载工作台工具组件；配置中心沿用预设选择。 |

   | 任务读取结果 | 指定 Task ID 的数据，以及该任务类型需要的字段用途和引用关系说明。 | 在工具的 `output.render` 中按任务类型选取说明。 |
   | Tool 执行方法 | 调用业务服务、保存产物、返回结果和错误。 | 复用 WorkbenchService、运行时 schema 和现有存储。 |

   | 工具名称 | 参数来源 | 执行方法 | 返回内容 |
   | --- | --- | --- | --- |
   | `workbench_task_get` | `taskGetRequestSchema`，以 `task_id` 定位。 | `WorkbenchService.getTask()`。 | 第 5.2 节输入、产物、回答、轮次及该类任务的使用说明。 |

3. 工具组件的参数 schema 由 [schema.ts](../../src/workbench/schema.ts)派生。执行时从 Harness 的 Tool 执行上下文取得会话、Tool Call 与取消信号，沿用业务服务的身份解析和权限规则。模型只传业务参数。
4. [共享预设组合](../../agent-presets/shared/agent.cordis.yml)加载工作台工具组件。用户在 Agent Studio 创建的预设可以复用该组件，并组合不同的角色提示词、MCP、Skill 和其他工具。配置中心为各功能选择预设，同一个预设可以执行多种功能。
5. 创建任务时，工作台按绑定的预设 ID、提供商、模型和推理等级创建 Harness 会话。Harness 负责工具声明与 Skill 目录的呈现；Agent 根据工具用途完成任务。
6. 生成、Run 查询和读图继续复用现有预设能力。Skill 使用受管 CLI 时，其正文提供完整入口。配置中心任务提示词只维护本节第 1 项规定的内容。
7. 工具说明按以下方式保持单一来源，并逐步提供给 Agent。
   1. 字段类型、枚举与约束由运行时 schema 提供。工具参数声明与校验复用该定义。
   2. 字段含义、来源、使用条件、空值处理和分功能用法统一保存到拟新增的 `config/workbench-tool-descriptions.json`。实施者从 [managed-cli-help.json](../../config/managed-cli-help.json)提取对应业务说明，保留 CLI 自身的调用语法说明。
   3. 会话开始时提供工具用途和参数声明。读取任务后，仅返回该任务类型涉及的字段说明、参考资料关系和允许的产物类型。
   4. `output.schema` 校验工具返回值，`output.render` 生成 Agent 实际收到的数据与说明。验收以模型实际收到的内容为准。
   5. 原生 Tool 和需要展示相同业务字段的 CLI 从该结构化文件派生说明。原型中的 `WORKBENCH_TOOL_GUIDANCE` 提供本轮业务说明候选；实施时迁入该文件。
8. 用户告知原型提示词修改完成并认可后，实施者按以下步骤取得原文。
   1. 从用户审阅的浏览器读取 `http://127.0.0.1:18763` 的本地存储，键名为 `harness-experiment-workbench-prototype-v2`。
   2. 按工作区 ID 和功能 ID，提取 `functions` 数组中各项的 `kind` 与 `requestTemplate`，并与编辑框全文核对。
   3. 将工作区 ID、功能 ID、`kind` 和 `requestTemplate` 原文保存到配套的 `experiment-workbench-iteration-20261109.instructions.json`，供实施和验收读取。
   4. 实施者采用用户认可的完整原文；后续文字调整交由用户审阅。
9. 实施者在验收工作区逐项打开 10 种功能，核对默认要求、保存内容、`binding_snapshot_json` 和实际请求。实际请求与保存内容的差异只有 `{{task_id}}` 被替换为工作台任务 ID。
10. 工具装配验收使用两个工具组合不同的预设。验收者核对发往模型的工具名称、描述和参数，确认所选预设实际生效。随后验证任务读取、产物提交及实验结束。

#### 5.4.2 运行输入与参考来源

1. 右栏保留“准备运行”和“查看运行”按钮。“准备运行”显示已保存输入，用户点击其中的“编辑参数”进入编辑状态。历史 Run 以只读内容展示。
2. 编辑状态提供“取消”和“保存参数”。保存后的参数才进入任务提交。查看历史 Run、图片或参考内容时保留未保存编辑。
3. 新建工作的正负提示词为空。用户可以手填，也可以调用生成提示词功能。
4. 引用弹窗的“添加引用”保存参考关系。“使用此运行输入”和历史查看中的“用于下次运行”均复制所选 Run 参数并添加参考。复制的参数写入当前分支的编辑区，页面继续选中该分支。
5. 引用任务时，页面展示该任务的产物和具体 Run。用户可以引用没有 Run 的任务产物，也可以选择其中某次实际运行。
6. 用户在当前分支选择执行方式。“运行一次”对应“运行任务”按钮；“持续实验”对应“开始实验”按钮。点击按钮时，页面按当前分支创建任务。
7. Agent 参考图片必须经过读图工具。`reference_requirement` 提供观察重点；为空时结合原始需求和本次改进要求观察。读图失败时，Agent 记录错误与待核验内容，停止依赖该观察的判断。

#### 5.4.3 功能目标、数据用途与完成条件

1. 实施者逐项完成下表中的 10 种功能，并用真实 Agent 产物核对页面结果。

   | 功能 | 任务目标 | 输入数据的用途 | 真实产出 | 页面完成条件 |
   | --- | --- | --- | --- | --- |
   | 生成提示词 `prompt` | 将原始需求写成所选模型可用的提示词。 | 原始需求确定画面；改进要求确定本次重点。参考任务和 Run 提供既有写法，经验和读图结果提供可采用内容。 | `prompt` 含正负提示词及所用 Skill 的原生产物。尚未选择模板时，按已选模型完成提示词。 | 任务所属分支显示回填的提示词与来源；用户保存后，运行使用相同文字。 |
   | 改写提示词 `rewrite` | 按本次要求修改已有提示词。 | 当前提示词确定修改起点；继承 Run 提供原参数。多条经验分别判断适用性，图片观察对应参考要求。 | `prompt` 保留本次要求保留的内容，并体现指定修改。 | 编辑区显示修改后的提示词；来源 Run 和已提交任务保留原输入。 |
   | 建议参数 `parameters` | 给出符合画面目标与模板约束的参数值。 | 实际模板描述确定参数 ID、类型和范围。当前值、参考 Run 与图片观察用于判断调整方向。 | `parameters` 提供允许参数的具体值。 | 任务所属分支的参数字段回填可保存的值；再次运行采用这些值。 |
   | 推荐资源 `resources` | 为画面目标选择模型、模板和 LoRA。 | 需求确定资源用途；目录详情提供资源身份与兼容信息。既有选择和经验用于比较候选。 | `resources` 提供可查询的资源引用和选择依据。 | 页面展示候选；用户采用后，分支输入显示对应资源。 |
   | 分析结果 `review` | 判断实际图片是否达到本次目标。 | Run 输入说明生成条件；读图结果提供可见事实。评价草稿提供用户关注点。 | `review` 提供可见观察，以及包含适用局限的评价结论。有调整依据时提供候选输入。 | 评价表单回填对应 Run 的观察与结论；用户可修改并保存。 |
   | 比较结果 `compare` | 找出所选 Run 的差异并建议下一轮做法。 | 各 Run 的实际输入用于比较条件；图片观察用于比较结果。样本条件决定因果判断的范围。 | `review` 指明比较对象、可见差异与结论。有依据时提供下一轮候选输入。 | 比较页面展示各 Run 对应结论；候选输入可采用到任务所属分支。 |
   | 诊断失败 `diagnose` | 根据失败证据给出可执行的处理步骤。 | 失败 Run 的输入、状态和错误定位问题。实例、模型或节点查询用于核验判断。 | `review` 区分已知原因、待验证判断和处理步骤。 | 失败详情显示诊断内容与处理建议；Run 数量保持原值。 |
   | 整理经验 `experience` | 将已观察的做法整理为可独立使用的经验。 | Run 实际输入与图片观察提供证据；评价草稿提供待整理内容。正文与证据按第 5.2.3 节处理。 | `experience` 提供标题、适用条件、经验结论和可选出处。 | 表单回填后，用户可保存到全局经验库；经验卡可展示并供其他工作区引用。 |
   | 运行任务 `run` | 使用已保存输入完成本次生成。 | 固定输入确定资源、参数和图片；已有轮次用于继续等待已接纳 Run。 | 产生 1 个 Run，记录实际输入、终态和媒体或错误。 | 任务所属分支显示真实运行状态；详情可打开输出图片、实际参数和失败信息。 |
   | 持续实验 `experiment` | 在次数上限内迭代并判断画面目标是否达到。 | 首轮采用固定输入；后续采用本任务上一轮的 Run、读图结果和评价。剩余次数决定后续提交。 | 逐轮 `review`、需要调整时的 `generation_input`、Run 和结束结果。 | 页面展示本分支逐轮输入、图片与评价；次数和结束状态对应真实记录。 |

#### 5.4.4 产物采用与全局库

1. 提示词、参数和资源产物写入任务所属分支的编辑区；用户保存参数后用于后续运行。评价和经验产物回填所选 Run 的表单。已经提交的任务固定输入保持原记录。
2. 上部“经验”和“收藏”页签及数量显示整个工作台的数据。列表中的来源工作区、工作和分支用于识别出处；切换工作区后，库中的记录与数量保持一致。工作区尚未创建工作时，也能浏览两个库。
3. 经验列表、经验引用弹窗和收藏列表支持多选。“添加引用”把选中的经验与 Run 加入当前准备输入。不同经验保留各自的结论、条件和证据。
4. 收藏中的经验映射到 `reference_experiences`，收藏中的 Run 映射到 `reference_run_ids`。移除任务中的引用只改变本次输入；取消收藏只改变收藏记录。当前尚未选择工作时，引用操作提示选择或创建工作。
5. 用户采用 Agent 产物后，再创建运行任务的流程如下。

   ```mermaid
   %%{init: {'flowchart': {'curve': 'linear'}}}%%
   flowchart TD
     D[保存本次要求、参数与参考内容] --> T[在当前分支创建任务并固定输入]
     T --> A[Agent 按 Task ID 读取输入]
     A --> S[读取来源记录、图片观察和经验]
     S --> P[按 Task ID 提交提示词或参数产物]
     P --> E[回填任务所属分支编辑区]
     E --> SAVE[用户保存参数]
     SAVE --> RUN[创建运行任务并提交 Run]
     RUN --> RESULT[保存实际输入、图片与评价]
     RESULT --> NEXT[选择本轮结果作为后续参考]
     NEXT --> D
   ```

### 5.5 图片选择、绑定与传送

#### 5.5.1 图片交互

1. 右栏分别显示“Workflow 输入图片”和“Agent 参考图片”。两个区域在尚未选图时均显示标题，各自提供“从运行记录选择”和“选择本机图片”按钮。
2. Run 图片选择弹窗的标题显示图片用途，并支持跨工作区筛选和多选。本机文件选择使用 `multiple`。用户从哪个区域选图，图片就添加到哪个区域。
3. Workflow 图片卡片提供模板图片参数选择，Agent 图片卡片提供参考要求输入框。用户点击卡片上的“也用作 Agent 参考图片”或“也用作 Workflow 输入图片”，可将同一张图片用于两处。两个区域均显示该图片，并标注图片同时用于另一区域。
4. Workflow 图片参数描述补充图片基数：`one` 表示单图，`many` 表示有序多图；基数由节点输入定义与参数适配器提供。多个单图参数分别绑定图片；模板声明多图参数时，图片按列表顺序组成数组。
5. 图片尚未指定参数时，页面保留图片并显示“未指定图片参数”。更换模板或实例后，页面保留已选图片，并根据实际参数描述更新绑定选项。
6. 图片用途保存在 `ImageRef.purpose`。同一张图用于两处时，两个区域共用图片引用，用途为 `both`。从一个区域移除时，只清除该用途；从 Workflow 区域移除时，同时清除对应参数绑定。保存、刷新和查看历史输入均按用途分别展示图片。
7. 图片参数使用模板声明的真实数据结构；未完成的参数绑定在对应图片处显示具体待选项。

#### 5.5.2 图片处理流程

1. Host 接收本机选图，保存文件并返回 `file_id`。用户关闭文件选择窗口时，已有选择保持原状。
2. Run 图片使用 `run_id`、`media_id` 定位 Saved Media；本机图片使用 `file_id` 定位导入文件。Agent 读图时取得 Host 返回的本地文件路径。
3. `generation submit` 的请求同时提交本次输入中的图片引用与绑定。Host 对照任务固定输入或已接纳的候选输入读取这些结构。生成接纳后，Run 先记录提交输入。准备阶段按所选实例逐张上传 Workflow 用途图片，保存上传响应和参数对应关系。
4. Host 根据图片绑定，把上传返回值转换为模板需要的单图字符串或图片数组，形成 `effective_input_json`。编译器使用该输入生成实际 Workflow。
5. 图片准备失败时，Run 显示失败图片及具体错误。尚未准备成功时，实际输入保持为空，详情继续显示提交输入与失败信息。
6. 历史 Run 查询同时提供提交输入、实际输入和图片来源。再次引用时使用媒体或文件标识，由目标实例重新准备输入。

   ```mermaid
   %%{init: {'flowchart': {'curve': 'linear'}}}%%
   flowchart TD
     SELECT[选择 Run 图片或本机图片] --> REF[保存图片标识、用途与参考要求]
     REF --> AGENT[Agent 参考用途]
     REF --> WORKFLOW[Workflow 用途]
     AGENT --> READ[Image Reader 返回图片观察]
     READ --> CHANGE[Agent 生成提示词或调整参数]
     WORKFLOW --> BIND[按模板参数绑定一张或多张图片]
     BIND --> UPLOAD[Run 准备阶段上传目标实例]
     UPLOAD --> PARAM[记录响应并生成实际参数]
     PARAM --> RUN[执行 Workflow 并保存结果]
   ```

7. 使用两个工具组合不同的预设完成真实任务，记录模型收到的工具声明及选择结果。任务消息保持第 5.4.1 节规定的内容，验收过程中由 Agent 自行选择已注入的工具。
