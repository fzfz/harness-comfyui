# DeepSeek Harness Desktop 与本地插件升级方案

## 1. 名词定义

1. 基线为本机 ARM64 Desktop 0.2.2-rc.3、当前 Desktop Profile 及其插件数据。
2. 候选宿主为官方 ARM64 Desktop 0.2.2-rc.5。下文用 rc.3 和 rc.5 指代这两个宿主版本。

## 2. 总目标

1. 执行者完成 rc.5 与本机插件的隔离适配，并提交第 7 节规定的验收记录。

## 3. 现状调研

1. 2026 年 11 月 19 日，本机应用声明 rc.3，应用内配置的[官方更新源](https://download.deepseek.com/dsh-desk/feeds/mac-arm64/nightly-mac.yml)提供 rc.5。仓库基线为提交 `10fe01c`，插件版本为 0.55.1。
2. [上游标签差异](https://github.com/deepseek-ai/deepseek-harness/compare/dsh-v0.2.2-rc.3...dsh-v0.2.2-rc.5)涉及 DeepSeek 模型响应转换、LLM 错误、LiveShare 隧道、网页搜索路由和设置界面。搜索会随模型路由选择提供方。使用模型网关时，搜索端点需单独配置。详见[官方迁移指南](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-rc.5/docs/upgrade-guide/v0.2.2-rc.4/web-search-deepseek-model-default/guide.zh.md)。
3. [仓库包清单](../../package.json)中的 51 个直接开发依赖或 peer 依赖精确引用 rc.3。npm 官方注册表已发布全部 51 个包的 rc.5 版本。两版的 exports 映射逐包相同。目标包均未标记弃用，也未声明 preinstall、install 或 postinstall。按包名与目标版本查询 npm 批量安全公告接口，返回空对象。
4. 本机 Desktop Profile 的 bundles 包含官方 base、web-app 及下表中除 Atlas 外的5 个插件。Profile patch 中 Atlas 条目的 disabled 值为 false。

## 4. 面临的问题

1. 现有 ComfyUI 插件声明的宿主范围排除了 rc.5。SDK 导出名称相同，仍需通过类型检查和实际调用核对参数、返回值及行为。
2. Profile 副本会保留三个 link 依赖和 Agent Studio 的绝对路径。直接启动副本可能加载生产插件，导致验收结果失真。
3. 当前资料只证明浏览器桥接插件存在版本差距。是否需要改源码，取决于依赖解析、插件加载和扩展握手结果。

## 5. 问题的解决和实施方案

### 5.1 实施流程

```mermaid
flowchart LR
 A[记录 rc.3 基线] --> B[复制并隔离数据和插件]
 B --> C[在副本中切换 rc.5]
 C --> D[适配插件并逐项复验]
 D --> E[演练恢复 rc.3]
 E --> F[审批发布与生产切换]
```

### 5.2 实施步骤

1. 执行者依据基线应用的加载记录，核对各插件的启用状态、加载错误、版本和功能结果。执行者分别备份应用包、Electron user-data、Harness home、插件源码链接目标及其引用的外部 Workspace。执行者为数据库创建一致性快照，并记录恢复位置。凭据仅在本机按授权使用。
2. 执行者把链接目标和预设路径改指隔离副本，核对宿主路径、端口、Workspace、数据库和插件写入位置。执行者从同一快照创建两份副本，分别运行 rc.3 和 rc.5。先记录原插件组合的结果，再逐个替换候选插件。两份副本的初始启用状态均与基线一致。
3. 执行者在[包清单](../../package.json)中更新宿主、直接 SDK 和插件版本，生成锁文件。核对传递依赖公告、原生依赖及安装脚本后，按已批准的依赖清单安装。同步更新[Desktop 验收配置](../../config/desktop-e2e.json)、[插件包合同测试](../../tests/production/plugin-package.test.mjs)、[probe 合同测试](../../tests/production/official-desktop-probe.test.mjs)、[README](../../README.md) 和[版本说明](../releasenotes.md)。验收配置的 application.bundlePath 须指向隔离应用。编译错误按实际 SDK 契约修复。
4. 对第三方插件的失败，执行者先用同一份数据在 rc.3 重放。确认由宿主变化引起后，优先验证维护者发布的精确版本。本地源码插件在独立副本中修复并保留可恢复的旧版本。浏览器桥接插件需同时验证扩展协议。无法取得兼容版本或修复授权时，保留 rc.3 生产环境。
5. 执行者验证内置搜索在现有模型路由下使用预期端点和凭据来源；网关配置先核对目标域名，再发送测试请求。复现模型异常响应，核对当前请求返回的错误，并验证用户可继续发送消息。对已启用的 LiveShare，使用测试 Workspace 验证创建及关闭分享。
6. 执行者依据[发布规范](../system/releasing.md)提交审查和发布申请。生产切换前重新备份。任一已启用插件无法加载、历史数据无法读取或业务验收失败时，执行者停止候选应用。执行者恢复同一时点的 rc.3 应用、插件、Profile 和数据，再复验第 3 节的业务动作。

## 6. 方案待决策项清单

1. 建议批准隔离环境中的 rc.5 适配及第 5 节所需的官方测试应用、依赖安装和测试运行。第三方插件版本以逐项实测为依据。
2. 维护者根据候选插件、依赖审计结果和恢复演练记录，分别审批发行及生产切换。

## 7. 计划验收清单

1. 每个插件均有基线和候选记录，列明版本、启用状态、实际加载路径、表中业务动作及重启结果。隔离环境的路径记录必须能证明插件与存储均指向副本。
2. 基线中的会话、Workspace、Agent Studio 预设、ComfyUI 历史结果及附件均可读取。逐类记录升级前后的数量、样本 ID 和读取结果。新增测试数据可在重启后读取。
3. 执行者按[测试规范](../system/testing.md)运行目标合同测试、官方 Desktop E2E 和最终质量门禁。记录候选树、应用版本、安装包、测试结果及端口释放结果。
4. 执行者在独立副本演练第 5.2 节的恢复步骤。维护者核对恢复后的插件版本、历史样本及工作台任务结果。

## 8. 非本次目标

1. 本次升级范围之外的对象包括其他平台及独立的 Web、Headless Profile。

## 9. 已获得的授权

1. 用户已批准独立 worktree、只读调研和方案编写。安装、执行候选软件、修改插件及生产切换等待相应审批。
