## 2. 恢复测试覆盖与待澄清的验收解释

1. 原计划第 6 节第 1 项（第 1186 行）要求“凭据修正或服务恢复后，用户重新激活对应预设并执行一次目录查询”；补充计划第 5.4 节第 6 项（第 105 行）要求测试“恢复后重新激活成功”。
2. `tests/desktop/official-desktop-live.test.mjs:832–880` 为三个失败场景分别执行 `failed`、`recovered` 阶段。`recovered` 阶段重新启动应用，明确断言两个项目预设的 `session.create` 成功，并分别执行 `exerciseOfficialMcpWorkflow()`；该函数断言搜索和详情调用成功且结果到达模型。第 899 行明确记录恢复模式为 `application-restart-after-environment-update`。
3. 同文件第 881–896 行额外记录服务恢复后的同进程激活结果。第 893 行仅遍历成功会话，因此该诊断不能证明两个预设均可在同一进程内恢复。其结果须按实际记录解释。
4. 两份批准计划均未明确要求“必须不重启应用”或“必须同一宿主内恢复”。将“重新激活”解释为强制同进程恢复属于审查推断，当前依据不足以判为 P2 缺陷。若最终验收要求同进程恢复，需要明确该解释并补充对应断言；已有重启恢复测试具有实际恢复断言。

1. 本轮定向执行 `official-preset-overrides`、`official-mcp-services`、`official-candidate-identity` 和 `installed-presets` 四份测试文件，31 项全部通过；`git diff --check` 通过。
2. 候选 Client 校验在源映射确定的区间内逐字节比较候选包内容；允许候选模块处于不同位置后仍保留来源比对。Profile 辅助函数从安装资源派生配置，定向测试覆盖表达式保留、独立覆盖及撤销覆盖。
