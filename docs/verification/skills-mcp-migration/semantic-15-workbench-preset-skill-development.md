# ComfyUI 产品预设与项目 Skill 开发规范语义审计

## 审计范围

1. 本次审计只读取 `docs/agents/comfyui-workbench-preset-and-skill-development.md` 第 1—127 行，依据任务提供的文字规范逐行判断；本报告未核实文档所述配置、源码或测试是否与实际实现一致。
2. 除下列修改项涉及的内容外，其余行通过本次语义审计；空行和 Markdown 分隔符随所属段落一并覆盖。

## 需修改项

### 1. 第 1 行前：补充文档用途和读取时机

1. 独立理解：本文规定预设、项目 Skill 及其 CLI 参考文档的开发与验收要求。
2. 理由：文件不是 `SKILL.md`，当前缺少规定的 YAML 头；“适用范围”正文不能代替所需字段。
3. 在第 1 行前插入以下完整文字：

```yaml
---
文档用途: 规定 ComfyUI 产品预设、项目 Skill 及其 CLI 使用参考文档的开发与验收要求。
读取时机: 创建或修改本文适用范围内的预设、项目 Skill 或 CLI 使用参考文档前读取。
---
```

### 2. 第 5—127 行：使用有序列表组织同层级要求

1. 独立理解：当前正文由普通段落、无序列表和表格共同组织开发要求。
2. 理由：任务要求标题下的同层级内容使用有序列表；当前普通段落和第 19—22、40—47、120—125 行无序列表未满足该要求。
3. 完整格式替换规则：保留通过审计的正文文字，将各标题下的独立要求逐项加上 `1. `、`2. ` 等连续编号；将现有无序列表的 `- ` 替换为有序编号。第 17、38、118 行只引出紧随其后的列表，删除且不替换。第 79—88 行表格改为八项有序列表，每项采用“原左栏标题：原右栏全文。”格式，原有句末句号只保留一个。其他修改项完成后，按最终章节顺序重新编号。

### 3. 第 11—13 行：消除配置值的重复定义和构建流程复述

1. 独立理解：这两段同时介绍预设源码入口、配置字段取值、注册入口及构建步骤；第 19—21 行再次规定预设身份。
2. 理由：身份要求应只定义一次；配置版本与构建调用先后属于配置或代码的事实，应由对应文件承载。本文保留开发入口和安装包必须包含的资源即可。
3. 将第 11—13 行替换为以下完整文字，身份取值继续由第 19—21 行规定：

> 两个产品预设的源码目录、预设身份字段和资源根目录配置见 `config/product-agent.json`，插件注册入口为 `agent-presets/presets.cordis.yml`。开发者必须确保插件安装包包含 `agent-presets/` 和 `.agents/skills/`，并使安装包内的预设引用使用包内相对路径。

### 4. 第 26—30 行：集中定义 Skill 来源和作用域

1. 独立理解：这三段要求项目 Skill 从仓库目录构建，安装后由两个项目预设从插件包读取。
2. 理由：第 26、28 行重复给出源码根目录；第 28 行复述模块定位算法、provider 参数和 Skill 数量，增加了与代码分叉的维护点；第 30 行再次解释包内来源。来源、配置入口和作用域可以集中表达。
3. 将第 26—30 行替换为以下完整文字：

> 开发者在 `config/product-agent.json` 的 `skills.sourceRootRelativePath` 指定目录中创建或修改项目 Skill，并从该目录构建插件包。两个产品预设通过 `agent-presets/project-installed-skills.mjs` 加载插件包内的项目 Skill；项目 Skill provider 的作用域仅覆盖这两个预设。其他预设的 Workspace 和用户级 Skill 行为由官方应用管理。

### 5. 第 59 行：以职责和调用契约替代内部 API 过程复述

1. 独立理解：工作台主 Agent 通过一个工具创建和继续子任务，子任务继承模型设置，并将结果返回主 Agent。
2. 理由：`startContinuable`、`sendMessage` 和拒绝列表的实现描述不增加调用方需要遵守的契约；配置入口可以承载这些细节。创建参数和续派身份仍有直接用途，应保留。
3. 将第 59 行替换为以下完整文字：

> `ComfyUI工作台预设` 的子任务工具配置见 `agent-presets/harness-comfyui-cli-candidate/agent.cordis.yml`。主 Agent 首次调用 `subagent_task` 时提供 `description` 和 `task`，续派时将首次返回的 `subagentId` 作为 `agent_id`。子 Session 必须继承父 Session 的模型与 Provider，且只执行主 Agent 委派的任务；宿主必须将子 Session 完成通知返回父 Agent，并禁止子 Session 再次委派。

### 6. 第 63 行：移除角色工具配置字段的逐项复述

1. 独立理解：迭代预设具有构图、生成、观察和比较四个角色工具，每个工具具有独立配置。
2. 理由：persona、模型字段、参数 schema 和任务模板字段的解释复述配置结构；创建返回值与续派返回值也应由工具声明承载。本文需要提供入口及必须保持的角色边界。
3. 将第 63 行替换为以下完整文字：

> `ComfyUI迭代预设` 的角色工具配置见 `agent-presets/harness-comfyui-iteration/agent.cordis.yml`，派发组件为 `agent-presets/project-iteration-dispatch.mjs`。开发者必须保留 `subagent_composition`、`subagent_generation`、`subagent_observation` 和 `subagent_comparison` 四个角色工具，并将子 Agent 的派生深度限制为一层。

### 7. 第 69—71 行：保留 Workspace 契约，引用实现入口

1. 独立理解：子 Session 开始工作前，宿主需要确认父子工作目录一致并将子 Session 加入父 Workspace；失败时中止该步骤并报告可操作的信息。
2. 理由：hook 名称、header 解析顺序、方法签名和完成结果复用方式属于组件内部流程。文档应规定可观察契约并指向实现入口。
3. 将第 69—71 行替换为以下完整文字：

> 两个产品预设均须加载 `agent-presets/project-subagent-workspace.mjs`。该组件必须在子 Session 首个 Agent step 前，确认父 Session 已加入 Workspace、父子 `cwd` 解析后的真实路径相同，并将子 Session 附加到父 Workspace。组件无法确认上述条件或无法完成附加时，必须停止当前 Agent step；错误信息必须包含子 Session ID、失败原因、与失败相关的父 Session、`cwd` 或 Workspace，以及使用者需要检查或修正的具体项。

### 8. 第 92 行：将 MCP 查询规范移出 CLI 参考文档章节

1. 独立理解：该段规定 Skill 的语义查询对象、查询工具来源和工具声明的信息职责。
2. 理由：本段不属于“项目 Skill 的 CLI 使用参考文档”；“Skill 在查询步骤中明确”也未直接指明编写者及其动作。“画师串”在全文没有定义，读者无法确定其与画师风格、Prompt 词条的区别。
3. 将本段移至独立的 `## 项目 Skill 的 MCP 查询步骤` 标题下，并替换为以下完整文字：

> 开发者必须在 Skill 的查询步骤中写明要获取的业务对象及其用途，并指定执行者通过 NoobAI MCP 查询。执行者调用工具时，必须以运行时工具声明为准读取参数、返回结构、分页和错误处理要求。禁止在 Skill 参考文档中复制这些工具声明。

### 9. 第 96—100 行：消除读取规则重复并补全执行主体

1. 独立理解：该节要求匹配请求后读取 Skill，首次调用 CLI 前读取对应参考文档，而 MCP 资料按任务需要读取。
2. 理由：第 96 行第二句与第 98 行重复定义 CLI 参考文档读取时机；“MCP 步骤只读取”的执行主体不明确。
3. 将第 96 行替换为以下完整文字，第 98 行继续定义 CLI 参考文档读取时机：

> 用户请求符合项目 Skill frontmatter 的 `description` 时，使用 ComfyUI 产品预设的 Agent 必须完整读取对应 `SKILL.md`。Agent 必须通过官方前台 shell Tool Call 执行 CLI 使用参考文档定义的项目 CLI 命令。

4. 将第 100 行替换为以下完整文字：

> Agent 执行 MCP 查询步骤时，只读取当前任务需要的 Skill 资料与工具声明。

### 10. 第 106 行：为 Skill 黑盒验收要求提供明确入口

1. 独立理解：修改开发产物后，开发者需要完成对应自动化测试、启动检查和 Skill 黑盒测试。
2. 理由：“执行该 Skill 的应用规定的启动检查”与“该应用启动检查为该 Skill 定义的全部项目”没有对应入口，执行者无法从本文确定应采用哪些项目和通过条件；末句重复要求通过测试。
3. 将第 106 行替换为以下完整文字：

> 开发者修改产品预设、注册组件或相关 Host Tool 作用域时，必须运行覆盖所改行为的正常、异常和边界自动化测试。开发者修改项目 Skill 或 CLI 使用参考文档时，必须完成相应 Skill 的黑盒测试。测试范围、通过条件及提交、构建和发布所需检查以 `docs/system/testing.md` 为入口。

### 11. 第 116 行：使用可定位的审计规范名称

1. 独立理解：本段限制 Reviewer 的输入范围，要求每次独立审阅一个目标文件。
2. 理由：“内容写作”和“Skill 使用与开发”未在本文定义，且不是本次提供的仓库规范名称，执行者无法据此定位审计依据。
3. 将第 116 行替换为以下完整文字：

> 修改本规范、项目 `SKILL.md` 或 CLI 使用参考文档后，开发者必须派发独立语义 Reviewer。Reviewer 的输入只包含一个目标文件、仓库 `AGENTS.md` 中的“markdown和文字内容规范”及本节审计标准；审阅 Skill 文件时，还须提供“Skill开发规范”。Reviewer 必须独立逐行阅读目标文件并判断语义质量。

### 12. 第 121、124 行：消除正向句式要求与 Skill 禁止性规范的冲突

1. 独立理解：当前条款要求每条规则及限制条件都使用正向句式，同时要求只有反复测试出现同一错误后才能保留限制条款。
2. 理由：适用的 Skill 开发规范明确要求使用否定或禁止性语句说明规范和流程；当前条款反而要求全部正向表达。限制条款是否必要应由任务边界和执行需要判断，“反复测试中出现同一错误”不是所有必要限制的前提。
3. 将第 121 行替换为以下完整文字：

> 每项规则写明具体动作、对象所属文件或模块及执行条件；每章正文服务于该章用途，每项要求只完整定义一次。Skill 规范和流程必须遵守仓库“Skill开发规范”规定的句式要求。

4. 第 124 行保留前两句，将最后一句“限制条款须以正向句式说明允许执行的动作，并以反复测试中出现同一错误动作为依据；”删除且不替换。
