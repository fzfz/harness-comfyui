# worktree-development.md 语义审计

## 1. 审计范围与覆盖结论

1. 本次审计仅阅读 `docs/agents/worktree-development.md` 第 1—37 行；除下列需修改项外，其余内容通过本次逐行语义审计。

## 2. 需修改项

1. **第 1 行之前：补充文档用途和读取时机。** 当前文件直接以标题开始，缺少非 `SKILL.md` 文档要求的 YAML 字段。建议在标题前插入：

   ```yaml
   ---
   文档用途: 提供独立 worktree 的官方 Desktop 自动化验收和交互调试入口。
   读取时机: 开始、验收、查询或停止独立 worktree 的官方 Desktop 实例前。
   ---
   ```

2. **第 5—9、13—31、35—37 行：将同节内容组织为有序列表。** 当前前两节使用无编号段落，最后一节使用无序列表，不符合指定的同层级内容组织规范。完成下列文字替换后，将各节剩余段落分别改为从 `1.` 开始的有序列表；将第 15—19 行代码块缩进到对应操作条目，将第 35—37 行的 `-` 依次替换为 `1.`、`2.`、`3.`。

3. **第 5、7、9 行：保留验收入口和证据要求，移除实现步骤复述。** 当前文字逐项复述命令内部的构建、安装和连接顺序，并罗列测试已经负责的断言。读者需要知道执行入口、隔离配置来源和成功依据；具体执行步骤应由命令及测试文件承担。第 9 行的“候选树”也没有给出具体对象。建议将三段依次完整替换为：

   > 开发者在独立 worktree 中运行 `pnpm test:desktop`，验收当前 worktree 中的候选插件。验收范围见 `tests/desktop/` 中的 fixtures 和测试文件。

   > 自动化验收使用 `config/desktop-e2e.json` 定义的默认 `fresh` 隔离模式。测试完成后，开发者核对验收记录，确认本轮应用进程已退出、端口已释放。

   > `pnpm test:desktop` 的通过结果用于确认插件安装、界面和业务测试通过。交互调试命令用于查询应用进程与 Renderer（应用渲染进程）的运行状态。

4. **第 13、21 行：在命令示例前定义 probe，并删除停止实现细节。** 当前文件先使用 `probe`，后文才让读者推断其含义；第 21 行的 PID、进程组和信号核对流程属于脚本内部逻辑，读者没有对应操作。建议将第 13 行完整替换为：

   > 开发者使用已安装的官方应用进行交互调试时，运行 `official-desktop-probe.mjs`（下称 probe）。以下命令依次用于启动、查询和停止应用；执行查询和停止命令时，开发者将 `<run-id>` 替换为启动命令返回的 `runId`。

   将第 21 行完整替换为：

   > `runId` 标识本轮进程、端口、运行记录和证据。调试结束时，开发者执行 `stop`，并核对停止结果，确认本轮进程已退出、端口已释放。

5. **第 23 行：引用目录配置，删除租约实现复述。** 当前文字在引用目录配置后又列出具体持久目录，形成需要同步维护的第二份目录说明；`active-probe.json` 的租约机制属于脚本实现。读者真正需要遵循的是持久数据的复用范围和启动顺序。“本轮唯一运行材料”没有明确说明材料类型。建议完整替换为：

   > `development` 模式复用当前 worktree 的持久 Harness home、Electron user-data 和 Workspace。持久目录与每轮运行记录、证据目录的配置见 `config/desktop-e2e.json`。开发者在同一 worktree 中开始下一轮交互调试前，先停止上一轮实例。

6. **第 25 行：保留首次初始化操作，引用初始配置来源。** 当前段落同时承担用户操作说明、初始模型配置副本和 Profile patch 更新逻辑说明，混合不同职责。具体模型 ID、凭据引用和逐字段覆盖行为应由配置与脚本提供，删除这些复述不影响开发者执行初始化。建议完整替换为：

   > 开发者首次使用持久目录时，通过官方应用完成 Profile 初始化，并配置 Provider 和模型。后续交互调试复用已保存的 Profile、Provider、模型、插件设置、Workspace 和业务数据。首次初始化所用的 Profile patch 配置见 `config/desktop-e2e.json` 的 `initialProfilePatches`。

7. **第 27—29 行：合并凭据入口，移除重复配置和用途说明。** 第 27 行引用配置字段后，又重复列出必需与可选变量，并反向解释其他字段的处理；第 29 行再次引用同一配置，却没有提供额外操作。开发者需要一个凭据来源入口和明确的准备动作。建议将两段合并替换为：

   > 开发者按照 `config/desktop-e2e.json` 的 `environmentFilePath`、`credentialEnvironmentNames` 和 `requiredEnvironmentNames`，在 main checkout 的 `.env` 中准备本轮应用需要的凭据。probe 从该文件读取配置声明的凭据，并传给本轮应用进程。

8. **第 31 行：明确故障证据的读取动作。** 当前段落混用 `evidence` 和“证据”，末尾关于不存在的子命令的说明不帮助读者读取文件；准备阶段失败文件又仅用抽象的“配置”定位。建议完整替换为：

   > 开发者排查启动失败、端口冲突、取消、超时或清理失败时，读取本轮证据目录中的 `run.json`、stdout/stderr 文件和 JSON 证据文件。准备阶段失败时，开发者读取 `config/desktop-e2e.json` 指定位置的 `preparation-failure.json`。
